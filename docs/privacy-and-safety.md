# Privacy and Safety Model

`labcheck` is designed to be safe to host as a public static site and safe to run as a local-first audit tool.

The short version:

- No API keys are required.
- No paid inference service is called.
- No hosted backend is required for the public browser demo.
- The browser demo does not upload selected local files.
- The CLI does not execute target project code by default.
- Public GitHub URL scans are limited to public repositories.

---

## Browser Demo

The browser demo runs in the visitor's browser tab. When someone chooses local notebooks, files, or folders, the static page reads those files with browser file APIs and analyzes them client-side.

The browser demo does not send selected local files to a `labcheck` server because there is no `labcheck` server behind the static page.

When someone enters a public GitHub repository URL, the browser calls GitHub's unauthenticated public API directly from the visitor's browser. That path is intentionally bounded: it fetches public text-like files only, prioritizes README/manifests, runtime files, CI workflows, Docker/Make files, notebooks, and Python source, and caps file count and size.

Use the CLI for full scans of large repositories.

---

## CLI and GitHub Action

The CLI performs deterministic static analysis. It reads files, parses notebooks and source text, and produces reports.

By default, it does not:

- run notebooks
- execute Python modules from the target repository
- install target dependencies
- call an LLM
- send source code to a hosted service

Public GitHub URL targets are cloned into a temporary local workspace, scanned, and then removed.

The GitHub Action wraps the same CLI. The workflow generated by `labcheck init` requests only `contents: read` and does not need repository secrets unless the user adds their own workflow steps.

---

## What Not To Scan

Do not paste, upload, or scan private code unless you have permission.

Do not publish generated reports if they expose:

- private file paths
- internal dataset names
- unreleased research directions
- proprietary package names
- credentials, tokens, keys, or secrets

`labcheck` tries to make safe public use easy, but it cannot know every organization's confidentiality boundary.

---

## What The Score Means

The score is a reproducibility and handoff signal, not a scientific-validity judgment.

A low score means the scanned files contain evidence that a fresh clone may be hard to rerun or hand off. A high score means the checked surface looks cleaner; it does not prove that the research result is correct.

Use findings as prompts for review, documentation, and fixes.

---

## Deployment Safety

The safest public deployment is a static export:

```bash
python scripts/build_static_site.py
```

Then publish `dist/site` to GitHub Pages, Netlify, Cloudflare Pages, Oracle Object Storage, or another static host.

Avoid adding a hosted clone queue, backend worker, or paid inference endpoint unless you also add authentication, rate limits, quotas, queue bounds, and abuse monitoring.

---

## Maintainer Promise

`labcheck` should stay:

- no-key by default
- local-first
- deterministic
- clear about limitations
- respectful in generated outreach and issue drafts
- safe to demo publicly without creating a compute or secret-management liability
